Resumo Técnico — Programação Orientada a Objetos

Sistema Acadêmico Integrado — PlataformaEnsino

Projeto Integrado Multidisciplinar III · Universidade Paulista — UNIP · 2025

Nota: este documento descreve a estrutura que será implementada na próxima sprint do projeto. Os conceitos de Orientação a Objetos aqui detalhados — abstração, herança, polimorfismo e encapsulamento — representam decisões de design do domínio a serem codificadas em C# com ASP.NET Core e Entity Framework Core. Nenhuma funcionalidade descrita encontra-se ainda em produção.

1 Abstração

A classe Usuario será declarada como abstract em C#, o que impedirá que objetos do tipo base sejam instanciados diretamente. Essa decisão de design garantirá que todo ator do sistema possua um perfil definido — Aluno, Professor, Coordenador ou Admin —, centraliza a lógica compartilhada em um único ponto e elimina duplicação de código nas subclasses.

No banco de dados, a hierarquia será mapeada pelo Entity Framework Core com a estratégia Table Per Type (TPT): a tabela Usuarios guardará somente os atributos comuns da classe base, e cada subclasse concreta (Alunos, Professores, Coordenadores, Admins) terá sua própria tabela, ligada 1:1 a Usuarios pela chave primária compartilhada. A coluna TipoUsuario continuará indicando o perfil do registro, mas apenas como informação de apoio — não será usada pelo EF Core como discriminador de tabela.

Tabela 1 – Atributos e métodos da classe abstrata Usuario

Atributo / Método Tipo Modificador Descrição

Nome string(150) required Nome completo do usuário
Email string required Endereço de e-mail único na plataforma
Cpf string(11) required CPF com exatamente 11 dígitos, sem formatação

2 Herança

Quatro classes concretas herdarão de Usuario, cada uma representando um perfil distinto da plataforma. A herança permitirá que as subclasses reaproveitem todos os atributos e comportamentos da classe pai e acrescentem somente os elementos específicos de cada papel.

2.1 Aluno

Representará o estudante matriculado em cursos da plataforma. Além dos atributos herdados de Usuario, possuirá Matricula (código da matrícula institucional) e a coleção Matriculas (lista de matrículas em cursos, associação 1:N). A turma atual do aluno não será um atributo próprio — será derivada em tempo de consulta a partir da matrícula aprovada mais recente (Matriculas → Turma), evitando um dado duplicado que poderia ficar desatualizado. Sobrescreverá ExibirDados() acrescentando perfil e número de matrícula.

2.2 Professor

Representará o docente responsável pela criação de conteúdo didático e avaliações. Incluirá os atributos Especialidade (área acadêmica de atuação) e CodigoRegistro (registro profissional), além das coleções QuestoesBanco, ConteudosDidaticos e AvaliacoesPublicadas. Sobrescreverá ExibirDados() acrescentando perfil e especialidade.

2.3 Coordenador

Representará o gestor acadêmico, podendo responder por um ou mais cursos. Possuirá apenas CodigoRegistro como atributo próprio — o(s) curso(s) sob sua responsabilidade não será(ão) um atributo do Coordenador, e sim derivado(s) da ponta oposta do relacionamento (Curso.CoordenadorId), já que um coordenador pode responder por vários cursos ao mesmo tempo. Sobrescreverá ExibirDados() acrescentando apenas o perfil.

2.4 Admin

Representará o administrador da plataforma com acesso irrestrito. Não possuirá atributos exclusivos — herdará integralmente os atributos de Usuario. Sobrescreverá ExibirDados() indicando o nível de acesso total ao sistema.

Tabela 2 – Visão geral da hierarquia de herança

Subclasse Papel na Plataforma Atributos Exclusivos Associações Diretas

3 Polimorfismo

O método ExibirDados() será declarado virtual na classe Usuario e sobrescrito (override) em cada uma das quatro subclasses. O comportamento do método variará conforme o tipo concreto do objeto em tempo de execução, sem que o código chamador precise conhecer o tipo específico — característica central do polimorfismo em orientação a objetos.

Todas as implementações invocarão base.ExibirDados() antes de acrescentar suas informações específicas, demonstrando polimorfismo por extensão e não por substituição total do comportamento da classe pai.

Tabela 3 – Comportamento polimórfico de ExibirDados() por subclasse

Classe Modificador Informação Acrescentada ao Retorno da Base
Usuario virtual Nome, E-mail, CPF, Telefone, Endereço completo, Data de cadastro
Aluno override Perfil: ALUNO · Número de matrícula · Turma atual
Professor override Perfil: PROFESSOR · Especialidade acadêmica
Coordenador override Perfil: COORDENADOR · Curso responsável
Admin override Perfil: ADMINISTRADOR DO SISTEMA (Acesso Total)

Fonte: modelagem do domínio — PlataformaEnsino (sprint futura).

O polimorfismo também se manifestará na camada de autorização. O campo TipoUsuario, definido via ConfigurarAcesso(), será incluído como claim no token JWT emitido pelo endpoint POST /api/auth/login. Os controllers utilizarão o atributo [Authorize(Roles = "...")] para restringir endpoints com base no tipo concreto do usuário autenticado em tempo de execução.

Tabela 4 – Controle de acesso por perfil (polimorfismo de autorização)

TipoUsuario (claim JWT) Prefixo de Rota Escopo de Acesso

Coordenador /api/coordenador/** Gerenciamento de cursos, turmas, matrículas e professores vinculados
Professor /api/professor/** Criação de conteúdo, questões e avaliações — a nota é calculada automaticamente na correção

4 Encapsulamento

O encapsulamento será aplicado por meio de propriedades com modificador private set, impedindo que o estado interno dos objetos seja alterado diretamente por código externo à classe. Toda mutação de estado ocorrerá exclusivamente por meio de métodos de negócio controlados, que aplicarão as devidas validações antes de aceitar a alteração.

Tabela 5 – Propriedades encapsuladas e métodos de controle

Classe Propriedade Modificador Método que controla a mutação
Usuario SenhaHash private set ConfigurarAcesso() · AtualizarSenhaHash()
Usuario TipoUsuario private set ConfigurarAcesso() — definido uma única vez
Usuario Ativo private set Ativar() · Desativar()
Usuario DataCadastro private set Preenchido na criação — imutável após isso
Matricula Status private set Aprovar() · Rejeitar() · Cancelar()
Matricula NotaFinal private set LancarNotaFinal() — valida se status é Aprovada e se nota está entre 0 e 10
Matricula TurmaId private set VincularTurma() — valida integridade do identificador informado
Matricula DataSolicitacao private set RegistrarSolicitacao() — imutável após o registro
Avaliacao StatusPublicacao private set Publicar() · Arquivar() · VoltarParaRascunho()
Avaliacao ProfessorAutorId private set DefinirAutor() — atribuído uma única vez com validação
Avaliacao TentativasPermitidas private set DefinirTentativasPermitidas() — mínimo de 1 tentativa
Avaliacao PublicadoEm private set Preenchido automaticamente ao invocar Publicar()
